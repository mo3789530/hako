## Goal

The Workspace shell endpoint is now launched by
`hako-workspace-init` as a distinct unprivileged `hako-workspace-agent` after
the strict EFS mount hook succeeds. The root init gives it only the bound
Workspace/MicroVM identity, image-owned Gateway origin and public-key file, and
an inherited listener on a mode-0600 Unix socket. The `/run` hook waits for an
internal readiness probe; root proxies only `/v1/workspaces/...`, then stops
the child before unmount. Local supervisor tests cover this boundary. The
deployed Gateway and a real token/dialer connection, actual Podman/Lambda MicroVM image and `/dev/pts`
validation, and production key distribution remain open. See
[`Workspace Agent shell and PTY`](../docs/workspace-agent-shell.md).

Provide the in-MicroVM `hako-agent` protocol needed for lifecycle reporting and developer commands, without exposing provider credentials or long-lived access tickets.

## Work

- Define an authenticated, versioned agent control protocol and heartbeat/lease behavior.
- Keep AWS endpoint credentials short-lived and scope each token to the single bound MicroVM and agent port; never persist them in the journal or expose them in logs/API responses.
- Add a separate signed app-layer ticket because Lambda strips its reserved `X-aws-proxy-*` headers before forwarding to the guest. Bind the ticket to MicroVM, complete attempt identity, one operation, key ID, nonce, and expiry.
- Implement bounded exec, shell/PTY, process lifecycle, file transfer, service control, and cancellation with explicit resource and output limits.
- Keep Workload execution commands server-owned and fixed; do not accept arbitrary shell/argv from Repository input.
- Use Secret Manager references; fetch secrets only into the target process at runtime and redact outputs. Never persist plaintext into DSQL, image, EFS source tree, or logs.
- Add protocol compatibility/version handling, heartbeat loss behavior, and audit correlation IDs.

## Acceptance criteria

- Unit/integration tests cover authorization, PTY lifecycle, disconnect/reconnect, process cleanup, oversized requests/output, malformed frames, and secret redaction.
- Agent listens only on private Runtime interfaces; no public SSH or service/database ports are introduced.
- Document image build, update/rollback, protocol compatibility, and secret rotation.

## Progress (2026-10-12)

- Status update: the Workspace PTY is now connected locally to the TLS WSS Gateway through `workspaceagent.GatewayDialer`, which enforces its single-Workspace binding against signed claims. Gateway-to-real-PTY command/output E2E passes under `-race`; allowlisted port forwarding to `127.0.0.1` is also tested end-to-end. This supersedes the earlier status text above that said the PTY was not yet connected to WSS. Multi-Workspace routing, VS Code, and MicroVM `/dev/pts` validation remain.

- Controller-side AWS proxy token issuance is implemented for agent start, status, and result calls. Each token is limited to port 8080 and five minutes; missing/malformed token responses fail closed. Unit tests verify VM/port/lifetime scope and token issuance on status/result paths.
- Ed25519 ticket issue/verify library binds a five-minute maximum credential to a single MicroVM, complete attempt identity, and one of start/status/result. The Controller requires an injected issuer and creates a fresh operation ticket per call; credentials are omitted from JSON and never journaled.
- Start/Source tickets additionally sign the immutable source digest, commit SHA, and absolute execution deadline. The handler rejects a mismatched upload header or Start body before calling the installer/backend; status/result tickets cannot carry these execution fields. Unit and protocol tests cover altered execution inputs and reject unbound Start ticket issuance.
- Protocol-v1 client and HTTP handler/Controller adapter are implemented: fixed HTTPS Lambda MicroVM host validation, explicit AWS port 8080 routing, no environment proxy/redirects, 64 KiB JSON bound, strict version/identity validation, app ticket verification, and safe errors. AWS validates and strips its reserved proxy headers; the app ticket remains available to the guest verifier.
- A fake-backed protocol HTTP→process backend E2E verifies signed start/status/result/log retrieval, fixed attempt pinning, bounded and redacted logs, and content-digest validation. Client tests verify the operation route/auth headers and reject invalid media type or protocol, mismatched length, oversized payload, and digest tampering. The Agent retains only bounded logs in memory and does not call AWS/S3; Resource Plane Controller performs S3 persistence with its own role. This is local composition evidence only; the new listener executable is not yet started by a MicroVM image/run hook.
- This does not complete Task 45: production Agent-ticket signing-key provisioning/public-key image distribution, deployed Gateway↔MicroVM token/dialer validation, general process API, file transfer, service control, Secret reference execution, Lambda image-builder integration, and MicroVM validation remain outstanding. The local PTY, explicit Workspace UID/GID, and signed guest WSS shell endpoint are implemented and tested.
- A local `ProcessBackend` and `GoTestProcessFactory` run only the fixed `go test ./...` command after trusted resolver identity/spec checks, authenticated source-install record checks (attempt, archive digest, immutable commit), and deterministic re-archiving of the extracted source tree. The archive excludes `.git`, so commit binding is supplied by the trusted checkout/materializer and persisted by the authenticated source installer rather than inferred from guest Git metadata. A cancelled start request is rejected before launch; after accepted launch, the child receives a minimal environment, runs in its own process group, and is killed as a group on shutdown/deadline. Output is bounded and oversized output is withheld rather than retaining a possibly secret-truncated prefix. The Agent exposes completed redacted logs only through the short-lived operation-scoped `logs` ticket; S3 persistence belongs to the Resource Plane Controller, not the MicroVM.
- Added `FilesystemExecutionResolver` and `NewFilesystemAgent`: the resolver takes only signed execution claims and one absolute image-configured source path, and the composition wires it to the installer, ProcessBackend, and authenticated HTTP handler. Protocol end-to-end tests now exercise this composition rather than manually assembling its internal pieces. The HTTP server executable exists, while MicroVM image/run-hook startup, public-key image provisioning and production Resource Plane composition remain outstanding.
- Completed results are returned as defensive snapshots: mutating the returned artifact metadata cannot alter the cached idempotent result observed by a retry.
- The local image artifact now configures the listener and handles the documented `/run` identity hook, but the real Lambda image builder and Resource Controller runtime profile have not been provisioned or exercised. Arbitrary network egress is not blocked by the Go process environment; the MicroVM/VPC network policy PoC remains a hard gate and Workload creation stays default-off. Secret references, shell/PTY, file transfer, service management, and heartbeat/lease remain outstanding.
- `cmd/hako-agent` now provides the in-VM protocol listener at `0.0.0.0:8080`, graceful shutdown, bounded HTTP headers, and image-owned public-key file loading with rotation overlap support. The JSON key file is a map of key ID to unpadded base64url Ed25519 public key; the loader rejects malformed or oversized files, unknown fields, and more than 32 keys. The executable requires an image-owned source directory and does not accept listen-address overrides. No private signing key, AWS credential, or Secret value is loaded in the MicroVM. This is executable/library evidence, not proof that a Lambda MicroVM image or `/run` hook starts it.
- See [Lambda MicroVM Workload Controller](../docs/lambda-microvm-workloads.md) and [Workload Agent MicroVM Image](../docs/workload-agent-image.md) for image packaging, hook binding, the credential boundary, and remaining AWS gates.
- Added a distinct `internal/workspaceagent` Linux PTY manager for interactive Workspace shells. It accepts no caller-provided command, argv, environment, or cwd; uses only `/bin/sh -i` in the configured workspace root, minimizes the inherited environment, bounds session count/lifetime, terminal dimensions, and input frames, and kills the process group on cancellation/close/expiry. Real local PTY lifecycle and cleanup tests pass under the race detector. See [Workspace Agent shell and PTY](../docs/workspace-agent-shell.md). Gateway ticket validation, shell/port WSS relay, and local backpressure bounds now have tests; MicroVM `/dev/pts` validation, Gateway audit export, and production router remain open.
- Added `images/workload-agent/Dockerfile`, a local ARM64 ZIP artifact target, and documented image hook configuration. `/run` strict-decodes the provider MicroVM ID and bounded Controller identity payload, pins it idempotently, and makes the production listener require matching VM/attempt/execution tickets before handling operations. Unit tests cover pre-init rejection, same-payload replay, conflicting VM/attempt, wrong-VM/attempt ticket, altered execution binding, malformed payload, and body limits. The example key file is test-only; `make build-workload-microvm-artifact` requires an explicit public-key input. The Lambda image builder, real public-key provisioning/rotation, runtime hook behavior, and networking remain unverified.

It is packaged as `cmd/hako-workspace-init` and `images/workspace-init`, with a build-time pinned `amazon-efs-utils` RPM version. The root init now launches the interactive Workspace Agent as a separate unprivileged process after EFS mount, and local supervisor tests cover the handoff. The existing `images/workload-agent` remains Workload-specific and is not reused.
- The guest-side `GET /v1/workspaces/{workspace_id}/shell` WebSocket protocol is defined and tested. A one-use, two-minute Ed25519 Agent Ticket uses a distinct audience and binds user, Tenant, Workspace, Resource Plane, MicroVM ID, and shell permission; the guest pins those identifiers from the `/run` hook after EFS mount succeeds. The Resource Plane still lacks the Lambda token provider/remote stream dialer, and the root init does not yet launch the handler as an unprivileged child. AWS proxy tokens and Agent tickets remain separate; the parent Gateway must validate/revocation-check the Hako Session Ticket before issuing an Agent Ticket.
- Workspace PTY shells now support an explicit fixed UID/GID. When configured by a trusted runtime from the EFS Access Point identity, a root init can launch shells as the non-root Workspace owner; UID/GID 0 is rejected and an unprivileged manager cannot select a different identity. Tests verify the actual shell UID/GID and root/foreign-identity rejection. This hardens the PTY primitive but does not yet launch the Gateway-facing Agent as a separate process.
